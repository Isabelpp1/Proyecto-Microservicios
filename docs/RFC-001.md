# RFC-001 — Selección de stack tecnológico (resumen)

**Proyecto:** Sistema de Gestión de Pedidos para Tienda en Línea
**Autores:** Carlos Daniel Martinez, Douglas Pérez, Isabel Paiz
**Estado:** Propuesto (17 de julio de 2026)

## Decisión
Stack elegido: **Node.js + Express + MongoDB (Mongoose)**, con un API Gateway propio en Express
(`http-proxy-middleware`) y Docker + Docker Compose para la orquestación local.

## Por qué
- El equipo ya domina JavaScript/Node, lo que maximiza la probabilidad de completar el proyecto
  a tiempo dentro de las restricciones del curso.
- MongoDB permite iterar el modelo de datos sin migraciones formales, útil mientras el alcance
  del proyecto aún se está afinando.
- Cumple los patrones mínimos exigidos por el curso: servicios independientes, base de datos por
  servicio, comunicación síncrona entre servicios y un único punto de entrada vía Gateway.

## Alternativas descartadas
- **Python/FastAPI + PostgreSQL**: buena opción intermedia, pero no aporta ventaja decisiva sobre
  Node y añade curva de aprendizaje.
- **Java/Spring Boot + PostgreSQL/Kafka/Kubernetes**: ecosistema de microservicios más completo,
  pero su complejidad de configuración excede el tiempo disponible para un proyecto de curso de
  alcance acotado.

## Riesgos identificados y mitigación
| Riesgo | Mitigación |
|---|---|
| Poca experiencia previa con Docker Compose / networking entre contenedores | Sesión inicial de tutorial guiado antes de escribir código de negocio |
| Inconsistencia de datos sin transacciones distribuidas | Alcance limitado a 2–3 servicios con relaciones simples; llamadas síncronas con manejo explícito de errores |
| Tiempo insuficiente para mensajería asíncrona | RabbitMQ queda como mejora opcional; el MVP funciona 100% con REST síncrono |
| El Gateway "hecho a mano" puede fallar antes de la demo | Probar el flujo completo Gateway → servicios con al menos 2 días de anticipación |
